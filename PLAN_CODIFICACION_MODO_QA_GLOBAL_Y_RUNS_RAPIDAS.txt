======================================================================
1. OBJETIVO
======================================================================

Crear herramientas de QA utilizables en una Development Build de Android
para recorrer Quantum Forge con rapidez sin saltarse la logica real del
juego y sin contaminar una build publica.

El resultado debe permitir:

- Velocidad de simulacion seleccionable: x1, x5, x10 y x20.
- Ver siempre cual velocidad esta realmente activa.
- Acelerar todos los temporizadores ONLINE de jugabilidad que siguen
  activos.
- Mantener interfaz, animaciones y controles tactiles a velocidad normal.
- Avanzar exactamente +5 minutos, +30 minutos o +1 hora de tiempo de juego.
- Guardar y restaurar checkpoints manuales de QA.
- Volver a x1 en cualquier momento.
- No afectar el reloj real usado por progreso offline.
- No reactivar EM, ADP ni WHF.

Este modo sirve para verificar funcionalidad y progresion. No reemplaza una
run normal de balance.

======================================================================
2. ESTADO REAL DEL PROYECTO Y REGLAS DE ALCANCE
======================================================================

2.1. Recursos activos que SI deben avanzar con el tiempo simulado

- LE.
- Trazas.
- Produccion de los tres edificios base actuales.
- Fragmentos y sistemas actuales del Cuarto 2.
- Sincronizacion y efectos del Triangulo.
- Dimension 1: mineria, escaneos, exploraciones, misiones y trabajos que
  actualmente reciben dt por GameState.Tick / Dimension1System.Tick.
- Dimension 2: civilizaciones, actividades y temporizadores que actualmente
  reciben dt por Dimension2System.Tick.
- Dimension 3: estabilizacion, colas, diagnostico y automatizacion online que
  actualmente reciben dt por Dimension3System.Tick.
- Maquina: analisis de nodos.
- Cooldown de fusion del Cuarto 2.
- Convergencia de forma natural: las actividades de D1, D2 y D3 que otorgan
  sincronizacion/estabilidad deben completarse antes al acelerar su tiempo.

2.2. Recursos retirados que NO deben formar parte del modo QA

EM, ADP y WHF fueron retirados del juego activo.

Actualmente quedan residuos de codigo y guardado, pero:

- No existen edificios activos que los generen.
- Sus objetos de HUD estan inactivos.
- No deben producirse.
- No deben modificar LE.
- No deben aparecer en textos, logros, investigaciones ni herramientas QA.

2.3. Elementos que NO se aceleran

- Animaciones y transiciones de UI.
- Refrescos visuales de HUD/paneles.
- Pulsaciones, compras, elecciones o confirmaciones manuales.
- DateTimeOffset.UtcNow, lastUnix ni telemetria basada en tiempo real.
- Progreso offline al cerrar la aplicacion.
- Guardados automáticos medidos en tiempo real.

2.4. Prohibicion tecnica

NO usar Time.timeScale para implementar el modo QA.

La aceleracion debe hacerse escalando exclusivamente los segundos de
simulacion que entran a la logica de juego. Esto evita acelerar animaciones,
toques, coroutines visuales y ventanas del sistema.

BLOQUE 1. SERVICIO CENTRAL DE TIEMPO QA
======================================================================

Objetivo:

Crear una unica autoridad para la velocidad de simulacion. Ningun sistema
debe leer directamente un booleano local de DEV.

Archivo nuevo sugerido:

- Assets/Project/Scripts/QA/QaRuntimeService.cs

API minima requerida:

    public static bool IsAvailable { get; }
    public static float SimulationMultiplier { get; }
    public static bool IsAccelerated { get; }
    public static event Action<float> SpeedChanged;
    public static bool TrySetSpeed(float multiplier);
    public static float CycleSpeed();
    public static double ScaleOnlineSeconds(double realSeconds);
    public static void ResetToNormalSpeed();

Reglas:

1. IsAvailable solo es true si:

       Application.isEditor || Debug.isDebugBuild

2. Valores permitidos exactos:

       1f, 5f, 10f, 20f

3. Cualquier NaN, infinito, cero, negativo o valor no permitido se rechaza y
   deja x1.

4. En una build que no sea Development Build:

- SimulationMultiplier siempre devuelve 1.
- No se puede activar QA.
- Los controles QA se ocultan.

5. No guardar la velocidad en SaveData.

Se permite guardarla en PlayerPrefs con una clave exclusiva de QA para que
la Development Build del celular recuerde la seleccion. La build publica
siempre debe ignorar esa preferencia.

6. Default de una instalacion nueva: x1.

7. ScaleOnlineSeconds debe:

- Aceptar solo segundos finitos y >= 0.
- Devolver realSeconds * SimulationMultiplier.
- No modificar Time.timeScale.

8. Agregar un indicador de que QA se uso durante la sesion, solo para logs y
diagnostico. No debe alterar balance ni recompensas.

Validacion del Bloque 1:

- x1 escala 10 s a 10 s.
- x5 escala 10 s a 50 s.
- x10 escala 10 s a 100 s.
- x20 escala 10 s a 200 s.
- Valores invalidos no se aceptan.
- En modo no disponible el resultado siempre es x1.
- Time.timeScale permanece en 1.

Detenerse al terminar este bloque.

BLOQUE 4. AVANCE MANUAL DE TIEMPO
======================================================================

Objetivo:

Permitir avanzar trabajos reales sin regalar recursos directamente y sin
usar las reglas offline.

Archivo nuevo sugerido:

- Assets/Project/Scripts/QA/QaFastForwardRunner.cs

API sugerida:

    public bool IsRunning { get; }
    public float Progress01 { get; }
    public void RequestAdvance(double exactGameSeconds);

Botones exactos:

- +5 MIN = 300 segundos.
- +30 MIN = 1800 segundos.
- +1 H = 3600 segundos.

4.1. Regla principal

El avance solicitado representa segundos SIMULADOS exactos y es independiente
de la velocidad x1/x5/x10/x20 seleccionada.

Ejemplo:

- Pulsar +5 MIN siempre procesa 300 segundos de juego.
- No procesa 3000 segundos por estar en x10.

4.2. No llamar GameState.Tick(3600) una sola vez.

Procesar en pasos pequeños y deterministas, recomendado 1 segundo por paso.
La coroutine debe ceder control periodicamente, por ejemplo cada 50 pasos,
para no congelar el celular.

Por cada paso:

1. Calcular el multiplicador de analisis de Fase correspondiente al periodo.
2. Llamar GameState.Tick(step) SIN volver a aplicar el multiplicador QA.
3. Avanzar MachineManager.AdvanceAnalysis con step y el efecto de Fase.
4. Avanzar el cooldown de fusion del Cuarto 2 mediante un metodo publico
   controlado, si existe cooldown activo.

No llamar simultaneamente a GameState.Tick escalado y a los Tick internos de
D1/D2/D3.

4.3. No usar ApplyOfflineProgress para esta herramienta.

Las reglas offline tienen caps, exclusiones y autorizaciones distintas. El
avance QA debe representar tiempo online acelerado.

4.4. Guardado

- Guardar antes de comenzar.
- Desactivar botones QA mientras corre.
- Mostrar progreso y tiempo restante.
- Guardar al finalizar.
- Si hay excepcion, detener, mostrar el error y conservar el save previo.

No modificar manualmente lastUnix. El guardado final debe registrar la hora
real actual como siempre.

4.5. El avance manual NO debe:

- Comprar automaticamente.
- Elegir opciones.
- Confirmar misiones.
- Cambiar de panel.
- Ejecutar prestigios.
- Iniciar trabajos que el jugador no inicio.
- Completar requisitos que necesitan una decision manual.

Validacion del Bloque 4:

- +5 MIN procesa exactamente 300 s.
- Ejecutar 300 pasos normales de 1 s y usar +5 MIN produce el mismo estado
  determinista, salvo timestamps reales/logs permitidos.
- Los trabajos de D1, D2 y D3 en curso progresan.
- Analisis de Maquina progresa.
- El cooldown de fusion progresa.
- No se concede progreso offline adicional al reiniciar.
- La app no se congela durante +1 H.
- Pulsar dos avances simultaneos no crea dos coroutines.

Detenerse al terminar este bloque.

BLOQUE 5. CHECKPOINTS MANUALES DE QA
======================================================================

Objetivo:

Permitir volver a momentos importantes sin fabricar estados falsos.

No crear perfiles prediseñados que inventen progreso. Los slots guardan un
estado real alcanzado por el tester.

Archivos sugeridos:

- Assets/Project/Scripts/QA/QaCheckpointService.cs

5.1. Directorio

Usar una subcarpeta dentro de Application.persistentDataPath:

    qa_checkpoints/

Slots:

    checkpoint_A.json
    checkpoint_B.json
    checkpoint_C.json

5.2. Guardar checkpoint

1. SaveService.TrySave del estado actual.
2. Validar que save.json sea legible.
3. Copiar/escribir atomicamente al slot.
4. Guardar metadatos solo de QA: fecha real, dimensiones desbloqueadas,
   fase de Convergencia y velocidad QA usada.

No meter esos metadatos dentro del SaveData de produccion si no son
necesarios.

5.3. Restaurar checkpoint

1. Pedir confirmacion.
2. Crear automaticamente un checkpoint pre_restore recuperable.
3. Leer y validar el slot antes de reemplazar nada.
4. Actualizar lastUnix del estado restaurado a la hora real actual para que
   NO conceda progreso offline acumulado desde la fecha del checkpoint.
5. Reemplazar save.json de forma atomica.
6. Recargar Main.

Si falla cualquier paso, mantener intacto el save principal.

5.4. Compatibilidad

La restauracion debe pasar por las mismas migraciones de SaveService que una
partida normal. No duplicar una segunda implementacion de carga.

5.5. Build publica

QaCheckpointService no debe ser invocable desde UI de una build publica.
Los archivos QA no se incluyen ni se leen en una run normal.

Validacion del Bloque 5:

- Guardar A, progresar, cargar A y recuperar el estado exacto.
- Cargar no concede offline extra.
- Un JSON corrupto no reemplaza save.json.
- pre_restore permite recuperar el estado anterior.
- Checkpoints antiguos pasan por migracion.
- Los slots no aparecen en build publica.

Detenerse al terminar este bloque.
