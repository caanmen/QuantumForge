1. OBJETIVO DEL REDISEÑO
======================================================================

El juego ya posee su esqueleto funcional. Este trabajo no añade una nueva capa de
progresión: añade una capa de presentación que permita entender la progresión
existente.

Problema actual:

- Dimensión 2 separa las civilizaciones, pero muestra demasiadas subsecciones,
  botones bloqueados, requisitos futuros y texto desde la primera visita.
- Dimensión 3 muestra casi de inmediato producción, versiones, lotes, ensamblaje,
  inventario, colas, asignaciones, Banco, calibración, investigación,
  instalaciones, Consola, Diagnóstico y automatización.
- El jugador puede no distinguir qué debe hacer ahora, qué será relevante pronto
  y qué pertenece a una etapa muy posterior.
- firstEntrySeen es insuficiente para describir un onboarding de varias acciones.

Resultado esperado:

- Una acción principal inequívoca en cada etapa.
- Como máximo dos acciones secundarias nuevas junto a la principal.
- Información revelada por acciones y progreso reales.
- Sistemas activos siempre accesibles.
- Partidas antiguas y avanzadas no repiten tutoriales obsoletos.
- Ninguna bandera tutorial se convierte en requisito económico.
- El jugador puede cerrar, volver, guardar o progresar offline sin romper el flujo.

======================================================================
2. PRINCIPIOS NO NEGOCIABLES
======================================================================

2.1 LA LÓGICA DE DOMINIO SIGUE SIENDO AUTORIDAD

La UI nunca decide si una acción puede ejecutarse. Debe consultar los sistemas
actuales y sus métodos Can..., Is...Unlocked o Try....

La capa de presentación decide solamente:

- si una función se muestra;
- si se muestra como próxima o disponible;
- qué explicación contextual aparece;
- qué vista se abre de forma predeterminada;
- qué CTA se destaca.

Al pulsar, la acción vuelve a validarse mediante la API de dominio correspondiente.

2.2 PRESENTACIÓN NO ES DESBLOQUEO ECONÓMICO

Ocultar temporalmente una función durante el tutorial no debe cambiar sus fórmulas
ni sus requisitos reales. Si una partida ya cumple el requisito real o tiene una
actividad asociada en curso, la función se fuerza a visible.

2.3 UNA PANTALLA, UNA PRIORIDAD

Cada vista principal debe tener una tarjeta superior:

AHORA
[acción concreta]
[progreso o requisito inmediato]
[CTA principal]

Opcionalmente:

DESPUÉS
[próximo hito en una línea]

2.4 NO USAR SOLO BOTONES GRISES

No llenar la pantalla de opciones deshabilitadas. Usar los estados definidos en la
sección 4. Un botón visible bloqueado siempre debe explicar una condición cercana y
alcanzable.

2.5 NO OCULTAR ACTIVIDADES EN CURSO

Si existe una actividad persistente, su función debe estar visible aunque una marca
de presentación esté ausente:

- peregrinación;
- formación de Acólitos;
- rito activo;
- operación o Represalia;
- excavación o análisis;
- investigación;
- trabajo de producción, ensamblaje, instalación o investigación D3;
- calibración incompleta relevante;
- rutina o automatización activa.

2.6 NAVEGACIÓN SEGURA

Nunca ocultar:

- Atrás;
- Mapa de D2;
- Fábrica base de D3;
- Cerrar dimensión;
- Cancelar o gestionar una actividad activa cuando el dominio lo permita;
- acceso al resumen de colas cuando existe más de un trabajo o una cancelación
  pendiente.

2.7 SPOILERS NARRATIVOS

Permanecen ocultos hasta su evento canónico:

- Umbral Velado;
- Alerta de Civ 2;
- Contención;
- Anomalías;
- investigación/naturaleza del Ente;
- funciones futuras que el jugador todavía no puede interpretar.

4. ESTADOS VISUALES DE UNA FUNCIÓN
======================================================================

Crear un enum o equivalente:

Hidden
    No aparece. Aún no ayuda a decidir o es un spoiler.

Teaser
    Aparece como tarjeta/silueta de próximo objetivo. No abre controles completos.
    Debe mostrar un requisito inmediato y comprensible.

Available
    Puede abrirse y muestra sus controles normales.

Active
    Contiene una actividad en curso, resultado pendiente o riesgo actual. Se fuerza
    visible y debe recibir prioridad de navegación.

Completed
    Ya fue dominada/completada. Permanece consultable sin reclamar atención.

New
    No es un estado de autoridad separado; es un badge temporal aplicado a Available
    o Active hasta abrir o reconocer la función.

Precedencia obligatoria:

Active > Available/Completed > Teaser > Hidden

Una actividad activa nunca puede degradarse a Teaser o Hidden.

5. ARQUITECTURA PROPUESTA
======================================================================

Flujo:

GameState y sistemas existentes
        ↓
D2PresentationRules / D3PresentationRules
        ↓
FeaturePresentationState calculado
        ↓
D2PresentationRouter / D3PresentationRouter
        ↓
Paneles UI actuales

5.1 REGLAS PURAS

D2PresentationRules y D3PresentationRules deben ser funciones puras o casi puras:

- reciben GameState y el estado persistente de presentación;
- no modifican recursos, colas ni progreso;
- devuelven el estado visual de cada función;
- devuelven la CTA y siguiente objetivo;
- pueden inferir introducciones desde progreso monotónico.

No guardar fórmulas ni costes en las reglas de presentación. Consultar catálogos y
sistemas reales.

5.2 ROUTER POR DIMENSIÓN

Cada dimensión necesita un único coordinador de vistas.

Responsabilidades:

- abrir una screenId válida;
- cerrar subpaneles incompatibles;
- recordar lastScreenId;
- elegir una pantalla base segura;
- redirigir si una pantalla guardada ya no es válida;
- priorizar actividades activas;
- no manipular recursos ni requisitos.

Fallback D2:

1. actividad activa visible;
2. territorio actualmente seleccionado si sigue disponible;
3. Mapa;
4. Refugio de Civ 1.

Fallback D3:

1. actividad activa que requiere atención;
2. Fábrica base;
3. Producción V1;
4. pantalla de primera entrada si realmente nunca fue reconocida.

5.3 NO DEPENDER DE POSICIONES DE DROPDOWN

En D3 existen selecciones que hoy pueden depender de dropdown.value + 1.
Al filtrar versiones, MK o funciones bloqueadas, esa relación puede seleccionar un
ID incorrecto.

Todo dropdown filtrado debe usar una lista explícita visibleOptionIds:

- índice visual -> ID/version/MK real;
- repoblar conserva la selección por ID cuando sea posible;
- si desaparece una opción inválida, seleccionar la primera opción válida;
- no calcular una versión real únicamente sumando 1 al índice visual.

7. MIGRACIÓN Y PARTIDAS EXISTENTES
======================================================================

Al cargar una partida sin PresentationState:

1. Crear estado con presentationVersion actual.
2. Inferir funciones introducidas desde progreso persistente real.
3. Forzar como introducida toda función con actividad activa.
4. Calcular onboardingStage mínimo coherente.
5. No repetir tutoriales de una partida avanzada.
6. No eliminar IDs de presentación desconocidos; conservarlos e ignorarlos.
7. Normalizar listas y lastScreenId.

Inferencias D2 recomendadas:

- cualquier progreso de Civ 1 -> d2.c1.refuge;
- ofrendas o asignaciones de altar -> d2.c1.altars;
- peregrinación activa/completada o Confianza > 0 -> d2.c1.pilgrimages;
- Acólitos/Noviciado -> d2.c1.novitiate;
- rito activo o histórico -> d2.c1.rites;
- pactos desbloqueados/activos -> d2.c1.pacts;
- Umbral canónicamente disponible/preparado -> d2.c1.veiled_threshold;
- Civ 2 desbloqueada -> regiones y operaciones;
- Amenaza, protección o Represalia histórica -> defensa;
- fragmentos/mejoras -> resistencia;
- alertActive -> alerta;
- containmentAvailable/entityContained -> contención;
- majorPactEstablished -> pacto mayor;
- Civ 3 desbloqueada -> arqueología;
- restos/análisis -> análisis;
- archiveUnlocked -> Archivo;
- indicios -> clues;
- anomalía revelada/leída -> anomalies;
- entityResearchUnlocked/progreso -> entity_research;
- entityPactEstablished -> entity_pact.

Inferencias D3 recomendadas:

- initialized -> Fábrica;
- asignaciones existentes -> assignment_basic;
- piezas, trabajos o producción histórica -> producción;

- investigación o versiones V4–V6 -> research;
- cualquier instalación construida -> facilities y su feature ID;
- rutinas/perfiles de automatización -> automation;
- configuración offline válida -> offline_automation.

Si una partida avanzada cruza muchas introducciones, mostrar un resumen de máximo
tres novedades, no una cadena de veinte modales.

8. PATRÓN COMÚN DE TUTORIAL
======================================================================

8.1 COACHMARKS

- Máximo uno activo.
- Atenuar el resto únicamente durante las primeras acciones esenciales.
- No impedir Cerrar o Atrás.
- El pulso visual desaparece tras la primera interacción.
- No mover la cámara/panel mientras el jugador selecciona.
- Color acompañado por texto e icono.

8.2 AYUDA RECUPERABLE

Cada pantalla con tutorial debe ofrecer AYUDA o REPASAR.

- cerrar ayuda no bloquea progreso;
- volver a abrir reconstruye el paso desde el estado real;
- no reiniciar una introducción completa;
- las explicaciones vistas se pueden consultar después.

8.3 MENSAJES

Formato:

Resultado · cambio importante · siguiente acción opcional

Ejemplos:

Peregrinación completada · +18 Confianza · Civ 2 está más cerca.
MK1 construido · 1 libre · Asígnalo para reforzar el Banco.
No se pudo iniciar · faltan 30 Trazas.
Rutina pausada · reserva mínima de LE alcanzada.

No usar solamente “No disponible” o “Recursos insuficientes”. Indicar qué falta.

D3-11 — AUTOMATIZACIÓN
-----------------------------------------------------------------------

primero manual, después automático.

PATRÓN APRENDIDO · [acción legible]

CREAR RUTINA

1. Elegir patrón aprendido.
2. Definir reserva o parada.

- ACTIVAR;

- última ejecución;
- próxima condición;
- motivo de parada;
- reserva alcanzada;
- error persistente.

No comenzar con un dropdown masivo de acciones o IDs sin contexto humano.
